# Environment Interfaces

This section documents how each DSGBench game is wrapped so that an LLM agent can play it and the evaluator can compute metrics from the logs. For every game it records the **raw** observation and action spaces exposed by the game engine, the **wrapped** observation and action spaces exposed to the agent, the **prompt** sent to the LLM, the **output** expected from the LLM and how it is parsed, and which **evaluation data** the wrapper makes available.

## Unified wrapping pipeline

<div class="system-overview">
  <div class="module-card"><h4>1 · Native environment</h4><p>Game engine or third-party API exposes the full game state and low-level commands.<br><em>→ raw state</em></p></div>
  <div class="module-card"><h4>2 · Observation wrapper</h4><p>Organises the raw state into structured fields, then renders them as text.<br><em>→ structured observation</em></p></div>
  <div class="module-card"><h4>3 · Prompt assembly</h4><p>System prompt + recent observations + executed / failed actions.<br><em>→ prompt</em></p></div>
  <div class="module-card"><h4>4 · LLM decision</h4><p>The model returns analysis, suggestions and a decision list.<br><em>→ raw LLM output</em></p></div>
  <div class="module-card"><h4>5 · Output parsing</h4><p>Decisions are extracted and mapped to action IDs (exact match or similarity search).<br><em>→ action IDs</em></p></div>
  <div class="module-card"><h4>6 · Action execution</h4><p>The wrapper expands macro actions into low-level commands and logs results.<br><em>→ executed / failed actions</em></p></div>
</div>

## Comparison across games

Summary only; click a game for the full specification.

| Game | Raw observation | Raw action | Wrapped observation | Prompt structure | Wrapped action | LLM output | Evaluation data |
|------|-----------------|------------|---------------------|------------------|----------------|------------|-----------------|
| [StarCraft II](starcraft2.md) | Full game state via python-sc2: units and structures (type, position, health), resources and supply, upgrades, map, visible enemies under fog of war | Unit-level commands (ability + target); combinatorially large | Six dictionaries (resource, building, unit, planning, research, enemy) rendered as text summaries; plus executed / failed actions and process data | System prompt (role, 6-part analysis, 4-part suggestions, 72-action dictionary, ask for 5 decisions) + last 5 summaries + executed / failed actions | `Discrete(72)` macro actions: train, build, research, other (scout, attack / retreat, chrono boost, empty) | Markdown: analysis → suggestions → `Decisions` numbered list of 5 action names | Strategic planning, real-time decision and adaptive learning data available; social reasoning needs probes; team collaboration not applicable |
| [Civilization](civ.md) | civrealm text dict: units / cities (owner, type, position), diplomacy, fog-of-war map; per-actor `llm_info` with `available_actions`, minimap and upper_map | Freeciv directive strings (`move North`, `fortify`, `produce Settlers`), packed as (ctrl_type, actor_id, action) | Advisor global summary + per-entity text template: zoomed-out block statistics + zoomed-in 5×5 tiles + available actions + advisor message | Instruction / task prompt templates as user dialogue; two commands (`manualAndHistorySearch`, `finalDecision`); per-entity memory + Pinecone manual retrieval | `finalDecision` whose `input.action` must be one of the entity's `available_actions` | Forced JSON `{"thoughts": {thought, review, reasoning, plan}, "command": {name, input}}`; up to 10 attempts, then random action | Strategic planning data rich (per-turn EGI / UI / MPI / CER / TPI / CVP indices) and grounding_acc logged; real-time and team collaboration not applicable; no explicit win field |
| [Street Fighter III](streetfight3.md) | DIAMBRA dict: RGB frame 384×224×3 + per-player health, super_bar, wins, timer | Per-player discrete buttons 0–17 (8-direction moves, punches, kicks, combos) | No pixels: text summary of health, normalized distance (far / close), super-bar unlock hints, last actions, score advice (positions detected by pixel color) | System prompt (role, context summary, 21-move list, bullet format) + fixed user message `Your next moves are:` | 21 named macro moves (Move Closer, Fireball, Hurricane, Super attack 2/3/4, …) expanded per facing direction into button sequences | Bullet list `- <move>`; regex extract → lowercase validation against move list; re-query until at least one valid move | Real-time decision data available (synchronous vs asynchronous scenes, no-op frames while the LLM thinks); AHR / SMHR / HCR per frame and win / turns / time_use per match; social reasoning and team collaboration not applicable |
| [Diplomacy](diplomacy.md) | Full diplomacy `Game` object — no fog of war: units, supply centers, welfare points, order history, messages | MILA order strings (`A WAL - LVP`, `F NTH C A YOR - NWY`) via `set_orders`; free-text `Message` objects | Text blocks: dialogue history (LLM-summarized past phases), 3-phase order history, SC ownership, units with reachable destinations (VIA = convoy), SC / Units / WP scores | System prompt (role, welfare rules, JSON format, order syntax) + user observation blocks | Legal orders enumerated per phase type from `get_all_possible_orders`; messages as `{country-or-Global: text}` dict, up to 3 rounds per phase | Single JSON `{"reasoning", "orders": [...], "messages": {...}}`; orders coerced to strings, invalid orders skipped with error log | Social reasoning and team collaboration data available (full message table, allied / betrayal rates from the summarizer); WP / centers / units per phase; per-match eval matrix currently empty (wandb only) |
| [Werewolf](werewolf.md) | In-memory State / Player / GameView object tree: roles, private observations, votes, debate transcripts; aliveness implicit | Fixed state machine of 7 action types (remove, protect, investigate, debate, vote, summarize, bid) with player-name or text params | Per-player dict returned one player at a time: identity, round, private history, living list (shuffled), debate so far, legal `options` | Single user message from a Jinja template: rules + state + observations + role-conditional instructions + embedded JSON example | Candidate player names embedded in the output schema (`Choose from: …`); no action IDs | Two-field JSON `{"reasoning", <action key>}` via response schema; up to 30 retries, then random choice | Social reasoning and team collaboration data available (debate / vote logs, werewolf-pair coordination, per-round IRP / KSR / VSS); match result limited to winner + turns; strategic planning partial |
| [Stratego](stratego.md) | 34-layer 10×10 integer array (piece ranks, obstacles, partial-observability views, move tracking); unrevealed enemies = UNKNOWN | Flat 1D index: source square × (direction + distance), action size 2001 | Text board: own pieces `R(symbol)`, unrevealed enemies `B(#)`, lakes `~~~~`, plus `## Valid moves` and last-5 history moves | System prompt (rules, piece notation, strategy instructions) + user text board with worked example | Every legal move enumerated as a text line; answer is a `r c x y` string copied from the list | Markdown JSON block `{"reasoning", "move"}`; strict 7-char validation against the valid-move dict; ≥ 10 retries, then random move | Strategic planning data available (win, turns, live-piece rates / scores for both sides); opponent modelling visible in the required reasoning field; grounding_acc per side; social reasoning and team collaboration not applicable |

!!! info "Why this matters for evaluation"
    Fine-grained metrics are computed from what the wrapper logs: step timestamps, parsed actions and their execution results, resource and technology states, probe answers and ground truth. Each game page therefore ends with an **Evaluation data** table stating, per capability dimension, which data is already logged, which needs annotation, and what is missing.
